## Product Overview
修复"删除技能后残留空目录与孤儿文件"的缺陷 —— 元工具（`delete_own_skill` / `delete_shared_skill` / `delete_agent_skill`）删除技能时只删掉了入口文件 `SKILL.md`，导致技能目录残留。

现象：`nexus/data/tenants/t0/agents/poet/skills/` 下残留 `probe-main-agent-skill/`、`probe-tmp-del/`，`agents/joker/skills/` 下残留 `probe-joker-tmp/`，均为空目录（联调测试造的目标技能被删后留下的）。

## Core Features
- 删除技能时清理**整个技能目录**（`SKILL.md` + 附属文件 + 子目录），与管理端 `admin/skills` 口径一致
- 附属文件不再成为孤儿（D23 之后技能目录允许放任意文件）
- 同名重建技能时**不再继承**上一版的残留附属文件
- 清理现有 3 个残留空目录
- 补回归测试锁住该缺陷


## Tech Stack
- 语言：Go（模块根 `d:/proj/flame/nexus`）
- 存储抽象：`nexus/shared/storage`（`Storage` 接口统一 local / nfs / s3）
- 测试：`go test ./service/agent/...`（同包测试，可直接访问 `skillManager`）

## Implementation Approach

**根因**：`skillManager.Delete` 最后一步用 `storage.Delete`（删单个文件），而传入的 `m.skillPath(...)` 是 `.../skills/{name}/SKILL.md` 的**文件路径**（见 `paths.AgentSkillPath` 注释）。要递归删目录必须用 `DeletePrefix`。

对照：管理端 `admin/skills/admin.go` 的 Delete 用的是 `DeletePrefix(ctx, skillDirKey(...))` —— 说明这是元工具侧的**遗漏**，而非有意设计。佐证：同文件 `Update` 的改名分支**刻意做了整目录搬迁**，注释明确写了"只搬入口文件会把附属资源留在旧目录变成孤儿"，删除这条路径没有对应处理。

**改动 1（主修）**：`Delete` 末尾改为删除整个技能目录：

```go
	if err := m.repo.Delete(m.schema, s.ID); err != nil {
		return err
	}
	// 删**整个技能目录**（含 SKILL.md 与附属文件 / 子目录），与管理端 admin/skills 同口径。
	// 只删入口文件会留下空目录与孤儿附属文件；而且删除后重建同名技能时，
	// Create 的 WriteFile 会复用旧目录，旧附属文件会"复活"到新技能里。
	return m.storage.DeletePrefix(ctx, path.Dir(m.skillPath(ownerName, s.Name)))
```

- `path` 包已在 `skills.go` 中导入（`Update` 里用了 `path.Dir(oldPath)`），无需新增 import
- `DeletePrefix` 接口约定"目录不存在时返回 nil"，天然幂等
- 覆盖三个元工具：`delete_own_skill` / `delete_shared_skill` / `delete_agent_skill`（都走同一个 `Delete`）

**改动 2（加固）**：`Create` 写内容文件前，若目标技能目录已存在则先清空 —— 自愈历史残留，彻底堵死"旧附属文件复活"：

```go
	ownerName, err := m.ownerName(ownerID)
	if err != nil {
		return "", err
	}
	// 走到这里说明重名检查（FindByName）已过：库里没有同名 skill，磁盘上若还有同名目录
	// 必然是历史残留（旧版本删除只删了 SKILL.md）。先清干净，避免旧附属文件"复活"到新技能。
	skillFile := m.skillPath(ownerName, in.Name)
	if ok, eerr := m.storage.Exists(ctx, path.Dir(skillFile)); eerr == nil && ok {
		if derr := m.storage.DeletePrefix(ctx, path.Dir(skillFile)); derr != nil {
			return "", derr
		}
	}
	if err := m.storage.WriteFile(ctx, skillFile, []byte(in.Content)); err != nil {
		return "", err
	}
```

判断依据：能执行到此处时，`FindByName(m.schema, in.Name, ownerID)`（约第 316-322 行）已确认库中无同名记录。

**性能与可靠性**：local 驱动的 `DeletePrefix` 是 `os.RemoveAll`（单次系统调用）；S3 驱动是 `ListObjectsV2` + 批量删除（已有实现，内置分页），技能目录通常只有几个对象，无性能影响。`Create` 多一次 `Exists`（stat），可忽略。

## Implementation Notes
- **只改元工具侧**，不要动 `admin/skills`（它已经正确）
- 不要改动 `skills.go` 之外与本缺陷无关的逻辑；`service/rpc/server` 存在既有的 vet 报错（`non-constant format string`），与本任务无关，不要顺手改
- 测试须覆盖"含附属文件与子目录"的技能，不能只测单文件 —— 只测 `SKILL.md` 无法区分 `Delete` 与 `DeletePrefix`
- 现有残留目录的清理必须在代码修复**之后**做，否则清完还会被旧逻辑重新产生
- 本机 `Remove-Item` 会被 safe-delete 拦截，清理残留目录需用 `cmd /c "rmdir /s /q &lt;path&gt;"`

## Architecture Design
`skillManager.Delete` 是三个删除类元工具的唯一实现（`delete_own_skill` / `delete_shared_skill` / `delete_agent_skill` 的 Execute 都调它），所以单点修复即可覆盖全部入口；无需新增接口或抽象。

## Key Code Structures
测试所需的 stub 扩展（`skills_test.go` 同包）：

```go
// stubSkillRepoForDelete 只实现 Delete 流程用到的方法：FindByName（定位）+ Delete（记录）。
type stubSkillRepoForDelete struct {
	skillsrepo.Repository
	skill   *models.Skill
	deleted string // 记录被删的 skill id，供断言
}

func (s *stubSkillRepoForDelete) FindByName(_, name, _ string) (*models.Skill, error) {
	if s.skill == nil || s.skill.Name != name {
		return nil, nil
	}
	return s.skill, nil
}

func (s *stubSkillRepoForDelete) Delete(_, id string) error {
	s.deleted = id
	return nil
}
```

断言要点：删除后 `st.Exists(ctx, "tenants/t0/agents/joker/skills/old/docs/spec.md")` 与 `st.Exists(ctx, "tenants/t0/agents/joker/skills/old/SKILL.md")` 必须**都为 false**（当前代码下第一个会为 true —— 正是缺陷所在）。
