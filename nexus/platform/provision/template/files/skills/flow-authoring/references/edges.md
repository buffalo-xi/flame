# Edges: `create_edge` / `update_edge` / `delete_edge`

`create_flow` expresses branch sub-chains with `branches`; every other connection (child nodes inside a container,
`fork` / `wait` concurrency groups, rewiring, deleting) uses these three tools. They **touch `edges` only**: they create no
nodes and change no `config`.

> **The tools are the only authority on the rules**: handle shapes, positions available per type, hard blocks and
> per-position suggestions all live in `create_edge` / `update_edge`'s parameter descriptions — **the parameter
> descriptions and the errors win**.
> This document does not copy those rules — writing them in two places means one gets changed and the other forgotten, and
> the model then writes against stale wording.
>
> When unsure about a handle, **just call it**: a missing handle makes the error state the value to use based on the two
> nodes' positions; a poor combination returns `suggested_edge` (valid, already stored — apply it with `update_edge` to
> avoid routing around).

## The shape of an edge

```json
{"id": "04958", "source": "45063", "target": "07003",
 "source_handle": "source38245right", "target_handle": "target07003left"}
```

| Field | Meaning |
|---|---|
| `id` | edge id (a 5-digit string, generated by the tools and never colliding with node ids or sub-branch ids) |
| `source` | id of the node the edge leaves |
| `target` | id of the node the edge enters |
| `source_handle` | `source` + **handle owner** + position; the owner is usually the node id, and for `branch` / `intent` sub-branches it is `config.children[].id` |
| `target_handle` | `target` + **arrival node id** + position (the owner always equals `target`) |

Edges generated by `create_flow` carry handles too: the main chain is computed from the laid-out positions (same row
`right` → `left`), and the `source_handle` of a branch sub-chain's first edge is a **semantic key**
(`source<children[].id>right`; the executor finds the edge by prefix matching). Do not change it when you read it — changing
it breaks the branch.

## Usage

```json
// connect one edge
{"flow": "daily-sales-report", "source": "2", "target": "3",
 "source_handle": "source2right", "target_handle": "target3left"}

// outgoing edge of a branch sub-branch: the owner is children[].id
{"flow": "calc-branch", "source": "3", "target": "5",
 "source_handle": "sourcec1right", "target_handle": "target5left"}

// default-branch outgoing edge: the owner is the branch node's own id
{"flow": "calc-branch", "source": "3", "target": "6",
 "source_handle": "source3right", "target_handle": "target6left"}
```

```json
// rewire: changing target requires target_handle as well (the handle embeds the node id)
{"flow": "daily-sales-report", "edge_id": "04958", "target": "9", "target_handle": "target9left"}

// delete an edge
{"flow": "daily-sales-report", "edge_id": "04958"}
```

## Return values

| Tool | Returns |
|---|---|
| `create_edge` | `flow_id` `flow_name` `edge` `edge_count`; plus `replaced_edge` + `note` when it displaces an old incoming edge; plus `suggested_edge` + `handle_hint` when the handle does not match the position |
| `update_edge` | same as above, with `edge` being the updated edge |
| `delete_edge` | `flow_id` `flow_name` `deleted` (the removed edge) `edge_count` |

## Common misreadings

- **Mistaking a node id for an edge id**: `edge_id` may only come from `read_flow`'s `diagram.edges[].id`, never from `nodes[].id`.
- **Assuming `branches` and `create_edge` are mutually exclusive**: `branches` builds a branch node's outgoing edges; calling
  `create_edge` on the same `source_handle` in a flow that already has `branches` hits "one exit allows only one edge".
- **Connecting two outgoing edges to one node**: only `branch` / `intent` carry semantics for multiple outgoing edges (one per
  sub-branch). Every other node (including `fork`) allows a single outgoing edge. Note the tools deduplicate by
  `source_handle` only (`source<id>right` and `source<id>bottom` are two exits, each able to hold an edge), so "two outgoing
  edges from one node" is not blocked by the tool — it reports a `config` error at runtime (it used to silently follow the
  first only, and the second never ran).
- **Assuming you can connect nodes inside and outside a container**: a different `parent_node` is rejected outright; that is a
  hard canvas constraint.
- **Copying handles from this document**: there is no position table here; positions are defined by the tool parameter
  descriptions — when unsure, let the tool error out or suggest a value.
- **Not re-reading the structure after changing**: the edge tools only change edges and never touch node `config`; run
  `read_flow` once more before test-running again.
